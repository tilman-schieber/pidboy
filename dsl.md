# P&ID DSL Specification v0.1

A compact, human-writable, line-based DSL with optional indented block syntax for describing P&ID semantics. The DSL is intended to be generated by an LLM, edited by humans, validated deterministically, and compiled into a backend such as SVG or TikZ.

## Design goals

- Human-writable
- Text-based
- Not XML
- Not JSON
- Suitable for LLM output
- Easy to parse
- Backend-independent
- Semantic, not geometric

This DSL describes **what** is in the diagram and **how it is connected**. Exact placement, routing, and drawing geometry are handled algorithmically by downstream tooling.

---

## Core syntax

Each top-level object is a declaration.

A declaration has one of two surface forms:

### Inline form

```txt
<kind> <id> key=value key=value ...
```

Example:

```txt
line L100 class=process from=P101.out to=CV101.in
```

### Block form

```txt
<kind> <id>:
  key: value
  key: value
```

Example:

```txt
line L100:
  class: process
  from: P101.out
  to: CV101.in
```

## Rule: inline or block, not both

Valid:

```txt
equipment P101 type=pump at=(10,8)
```

Valid:

```txt
equipment P101:
  type: pump
  at: (10,8)
```

Invalid:

```txt
equipment P101 type=pump:
  at: (10,8)
```

---

## Grammar (EBNF-style)

```ebnf
document        ::= { blank | comment | declaration } ;

declaration     ::= inline_decl | block_decl ;

inline_decl     ::= kind ws ident { ws inline_prop } nl ;
block_decl      ::= kind ws ident ":" nl { indented_line } ;

indented_line   ::= indent ( property_line | nested_block | comment | blank ) ;
nested_block    ::= key ":" nl { deeper_indented_property } ;

property_line   ::= key ":" ws? value nl ;
deeper_indented_property ::= indent property_line ;

inline_prop     ::= key "=" value ;

kind            ::= "equipment"
                  | "valve"
                  | "line"
                  | "instrument"
                  | "signal"
                  | "group"
                  | "area"
                  | "note"
                  | "junction" ;

key             ::= ident ;
ident           ::= letter { letter | digit | "_" | "-" } ;

value           ::= scalar
                  | tuple
                  | list
                  | ref ;

scalar          ::= quoted | bare ;
quoted          ::= '"' { char } '"' ;
bare            ::= { bare_char } ;

tuple           ::= "(" value { "," value } ")" ;
list            ::= value { "," value } ;

ref             ::= ident [ "." ident ] ;

comment         ::= ws? "#" { char } nl ;
blank           ::= ws? nl ;

ws              ::= { " " | "\t" } ;
indent          ::= "  " { "  " } ;   # 2-space indentation only
nl              ::= "\n" ;
```

## Declaration kinds

The DSL supports these top-level declaration kinds:

- `equipment`
- `valve`
- `line`
- `instrument`
- `signal`
- `group`
- `area`
- `note`
- `junction`

Each declaration has:
- a **kind**
- an **ID**
- a set of **properties**

IDs must be unique across the document.

---

## Value syntax

### Scalars

Bare or quoted values:

```txt
type=pump
label="Cooling water pump"
```

### Tuples

Used for coordinates and similar compact structured values:

```txt
at=(10,8)
size=(4,2)
offset=(0,-2)
```

### Lists

Comma-separated values:

```txt
ports=in,out
members=P101,CV101,E101
```

In block form:

```txt
ports: in, out
members: P101, CV101, E101
```

### References

References use dot notation:

```txt
P101.out
E101.in
T101.vent
```

A reference may point to:
- an object, such as `TI101`
- an object port, such as `P101.out`

This is the canonical syntax for connectivity.

---

## Indentation rules

- Use **2 spaces per indentation level**
- Tabs are not allowed for indentation
- Nested blocks are allowed only for structured fields such as `ports:`
- Nesting should remain shallow

Recommended maximum nesting depth:
- top-level declaration
- one nested property block

Good:

```txt
equipment T101:
  type: tank
  at: (30,10)
  ports:
    inlet: west
    outlet: east
    vent: north
```

Avoid deeper arbitrary nesting.

---

## Semantics

This DSL is semantic, not geometric.

The source file defines:
- components
- ports
- typed connections
- instrumentation
- grouping
- annotations
- optional layout hints

The source file does **not** define:
- final routed polylines
- Bézier paths
- exact SVG paths
- exact symbol geometry
- collision resolution

Those are determined later by layout, routing, and rendering stages.

## Common conventions

### Coordinates

Coordinates are integer grid coordinates:

```txt
at: (10,8)
```

These are placement hints, not pixel coordinates.

### Orientation

Use one of:

- `north`
- `south`
- `east`
- `west`

### Locations

Typical instrument locations (each renders a distinct ISA-5.1 bubble):

- `field` — plain circle
- `panel` — circle with horizontal line
- `control_room` — concentric circles
- `shared` — circle inscribed in a square (shared display / DCS)

### Line classes

Typical line classes (rendered styles follow ISO 10628 / ISA-5.1
conventions; see README "Drawing conventions"):

- `process` — heavy solid
- `utility` — dashed
- `drain` — dash-dot
- `vent` — dotted

### Signal types

Typical signal types:

- `electrical` — dashed (ISA-5.1)
- `pneumatic` — solid with double-slash marks (ISA-5.1)
- `hydraulic`
- `digital`

## Declaration reference

## 1. equipment

Represents major process equipment.

### Required properties

- `type`

### Optional properties

- `at`
- `size` — symbol size in grid units, e.g. `(8,3)`; use for large
  multi-nozzle vessels. Vessels/tanks draw parametrically at that exact
  size (label moves inside the shell when it fits); other types scale
  uniformly.
- `ports`
- `label`
- `orient`
- `zone`

### Example

```txt
equipment P101:
  type: pump
  at: (10,8)
  ports: in, out
  label: "P-101"
```

Structured ports form:

```txt
equipment E101:
  type: heat_exchanger
  at: (24,8)
  ports:
    in: west
    out: east
    top: north
  label: "E-101"
```

Ports that share a side are distributed evenly along it in declaration
order (left-to-right for north/south sides, top-to-bottom for east/west).
A vessel can therefore carry e.g. `inlet: north, psv: north, vent: north,
gas: north` without the nozzles coinciding.

---

## 2. valve

Represents a valve as a first-class semantic object.

### Required properties

- `type`

### Optional properties

- `at`
- `actuator`
- `fail` — renders an FC/FO/FL tag beside the valve
- `state` — `nc` / `no`, renders an N.C./N.O. tag
- `ports`
- `label`

### Typical valve types

- `gate`
- `globe`
- `ball`
- `butterfly`
- `plug`
- `control_valve`
- `check_valve`
- `relief_valve`
- `safety_valve`

### Typical actuator values

- `manual`
- `pneumatic`
- `electric`
- `diaphragm` — renders the control valve with a dome (diaphragm) actuator

### Typical fail values

- `open`
- `closed`
- `last`

### Example

```txt
valve CV101:
  type: control_valve
  actuator: pneumatic
  fail: closed
  at: (16,8)
  ports: in, out
  label: "CV-101"
```

---

## 3. line

Represents a process or utility connection.

A `line` is semantic connectivity, not routed geometry.

### Required properties

- `class`
- `from`

### Optional properties

- `to` — omit it to draw an **open-ended stub**: a short run outward from
  `from` (drains, vents, sample points). Direction follows the `from` port
  side; without one, `vent` lines point up, `drain` lines down, others east.
- `label`
- `size`
- `spec`
- `route`
- `dir`

### Example

```txt
line L100 class=process from=P101.out to=CV101.in
```

```txt
line L101:
  class: process
  from: CV101.out
  to: E101.in
  label: "3in-P-1023"
```

---

## 4. instrument

Represents an instrument, indicator, transmitter, controller, alarm, or similar object.

### Required properties

- `type`

### Optional properties

- `at`
- `attach` — places the bubble next to the referenced object with a leader
  line. `attach: X.port` hangs the bubble outward on that port's side (a
  west port puts it left of the vessel with a horizontal leader); plain
  `attach: X` places it above.
- `location`
- `label`
- `loop`

### Example

```txt
instrument TI101:
  type: temperature_indicator
  attach: E101.top
  location: field
  label: "TI-101"
```

```txt
instrument TIC101:
  type: temperature_controller
  at: (24,3)
  location: panel
  label: "TIC-101"
```

---

## 5. signal

Represents a signal connection, separate from process lines.

### Required properties

- `type`
- `from`
- `to`

### Optional properties

- `label`

### Example

```txt
signal S100 type=electrical from=TI101 to=TIC101
signal S101 type=pneumatic from=TIC101 to=CV101
```

---

## 6. group

Represents a logical grouping of objects.

### Required properties

- `members`

### Optional properties

- `label`

### Example

```txt
group cooling_loop:
  members: P101, CV101, E101, TI101, TIC101
  label: "Cooling loop"
```

---

## 7. area

Represents an optional placement or zoning hint.

### Typical properties

- `label`
- `bounds`

### Example

```txt
area process_side:
  label: "Process Area"
  bounds: (0,0), (40,20)
```

---

## 8. note

Represents free annotation text.

### Typical properties

- `at`
- `text`

### Example

```txt
note N1:
  at: (5,2)
  text: "Normally closed during startup"
```

---

## 9. junction

Represents an explicit tee or branch point.

### Typical properties

- `at`

### Example

```txt
junction J1 at=(18,8)
line L102 class=process from=E101.out to=J1
line L103 class=vent from=J1 to=T101.vent
```

Junctions accept **directional taps** even though they declare no ports:
`J1.west`, `J1.east`, `J1.north`, `J1.south` give the connecting line (and
the placement of whatever hangs off it) a direction. This is how bypass
loops are written:

```txt
junction J1
junction J2
line B1 class=process from=J1.south to=BPV1.in
line B2 class=process from=BPV1.out to=J2.south
```

## Parsing and normalization

Both of the following declarations are equivalent:

```txt
line L100 class=process from=P101.out to=CV101.in
```

```txt
line L100:
  class: process
  from: P101.out
  to: CV101.in
```

They normalize to the same internal representation:

```txt
{
  kind: "line",
  id: "L100",
  props: {
    class: "process",
    from: "P101.out",
    to: "CV101.in"
  }
}
```

All downstream stages should consume the normalized AST rather than the original source text.

---

## Validation rules

A validator should enforce at least the following:

- declaration IDs are unique
- required properties exist for each declaration kind
- unknown properties are rejected
- enum values are validated against the active profile
- references resolve
- `from` targets exist; `to` targets exist when given (a line without
  `to` is a valid open-ended stub)
- referenced ports exist when ports are explicitly declared
- coordinates normalize to tuples
- indentation is valid
- a declaration is either inline or block, not both

---

## Routing and layout boundary

The DSL does not define routed paths.

The recommended pipeline is:

```txt
DSL source
  -> parser
  -> normalized AST
  -> validator
  -> layout engine
  -> routing engine
  -> renderer (SVG / TikZ / ...)
```

### The DSL defines

- equipment
- valves
- instruments
- signal connections
- process connections
- attachment points
- optional placement hints

### The layout/routing engine defines

- exact node positions
- orthogonal routing
- port assignment
- collision avoidance
- bend minimization
- label placement

---

## Recommended implementation notes

- Keep the language strict
- Keep nesting shallow
- Keep the source semantic
- Treat symbol geometry as a separate symbol-library concern
- Treat SVG and TikZ as output backends, not authoring formats

A stable architecture is:

```txt
LLM -> DSL -> AST -> layout/routing -> SVG/TikZ
```
